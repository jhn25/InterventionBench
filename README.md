# InterventionBench

**Can LLM Agents Adapt to Mid-task User Interventions?**
*Findings of EMNLP 2026*

Real users revise the goal while an agent is working: swap a target, add a request, drop a step, or cancel everything. **InterventionBench** measures how well LLM agents adapt when the goal changes mid-task, built on two stateful long-horizon environments: [AppWorld](https://github.com/StonyBrookNLP/appworld) and [WebArena](https://github.com/web-arena-x/webarena).

## How it works

Every instance pairs an original task **τ_A** with a revised task **τ_B** and is evaluated in three scenarios:

| Scenario | What the agent gets | What it measures |
|---|---|---|
| **A** | τ_A from the start | base capability |
| **B** | τ_B from the start | difficulty of the revised task alone |
| **A→B** | τ_A first, then the intervention arrives mid-task | adaptation |

**Adaptability** = success in A→B among the instances the agent can solve standalone in B, so a hard revised task is never counted against the agent.

## Intervention taxonomy

Each intervention modifies the task's **verb** (the action), **target** (the entity), or **both**, by one of three operations:

| | Verb | Target | Both |
|---|---|---|---|
| **Swap** | replace the action | replace the entity | replace the whole sub-task |
| **Add** | add an action | add an entity | add a whole sub-task |
| **Drop** | remove an action | remove an entity | cancel everything (*Cancel*) |

**2,250 instances** from **272 base tasks** (1,088 AppWorld + 1,162 WebArena), generated by an LLM pipeline and verified by a human audit plus execution-based evaluator screening.

## Key results (12 models, closed + open-weight)

- **Adaptability is low.** The best model preserves 71% (AppWorld) / 56% (WebArena) of what it can solve standalone; 11 of 24 model–domain results fall below 50%.
- **Add is the hard case.** Swap and Drop reach ~80% and ~78%, while Add collapses to 20% (AppWorld, pooled), lowest for every single model on both domains.
- **The added goal displaces the original one.** About three quarters of Add failures complete the added goal but lose the original, then declare both tasks complete.
- **Neither forgetting nor a step limit.** Agents still mention the original goal in ~93% of failing runs and stop on their own well before the budget; the same combined goal succeeds more often when given at the start.
- **Existing frameworks do not close the gap.** Eight planning/memory wrappers (Reflexion, AdaPlanner, Mem0, HippoRAG, ...) help on Swap/Drop but leave Add nearly unchanged.

## Quick start

```bash
pip install -r requirements.txt

# Recompute all scores from the released data
APPWORLD_ROOT=/path/to/appworld python scripts/score_add_assertions.py
python scripts/eval.py --results results/

# Run new inference (environments installed per their upstream repos)
python scripts/run.py --domain {aw|wa} --condition {A|B|A_to_B} --workers N
```

Scoring: Swap and Drop require the revised task to pass and the original to fail; Add requires both, checked per assertion on the final state; Cancel uses a trajectory-level stopping rule.

## Layout

- `data/` — intervention instances (JSONL; screened rows keep explicit `skip` flags) + `CHANGELOG.md`
- `src/interventionbench/` — runner, workers, and baseline framework wrappers
- `scripts/` — `run.py` (inference), `score_add_assertions.py` (Add scoring), `eval.py` (aggregate metrics)
- `results/` — released trajectories and aggregated metrics

## Dataset version

Current: **v1.1** (camera-ready). Every change is indexed in `data/CHANGELOG.md`. Known limitation: 44 BothAdd intervention texts carry a residual phrasing conflict (`data/known_limitations.json`), to be revised in v1.2.
